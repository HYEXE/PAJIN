# ADR 0021: 옵트인 방식의 Specialist 동시 실행

- 상태: Accepted
- 날짜: 2026-07-14

## 맥락

로컬 다중 에이전트 러너는 계획된 단계마다 Specialist 하나를 생성했지만 준비된 모든 작업을
순차적으로 실행했다. 이제 ADR 0020은 디스패치 전에 모든 Specialist의 최대 호출 횟수를
확정하므로 형제 작업이 루트 예산을 증폭하거나 빼앗을 수 없다. 서로 독립적인 오프라인 또는 읽기
전용 작업을 동시에 실행하면 특히 Web 및 Crypto CTF Suite의 Campaign 실행 시간을 줄일 수 있다.

등록된 모든 Tool을 병렬화하면 중지 조건이 약해지고 순차 실행을 전제로 설계된 상태 변경 작업이
겹칠 수 있다. 제한 없는 팬아웃은 로컬 Docker Worker를 지나치게 많이 시작할 수도 있다. 완료
순서대로 결과를 정리하면 검증과 보고서의 재현성도 떨어진다.

## 결정

`ToolSpec`에 기본값이 `false`인 `parallel_safe`를 추가한다. 동시 호출이 서로 독립적이고,
호출이 겹쳐도 부작용, 대상 동작, 비밀 사용, 증거 경로가 안전한 경우에만 Tool 작성자가 명시적으로
옵트인해야 한다. 위험 등급만으로는 병렬 안전성을 절대 의미하지 않는다.

계획 검증과 호출 할당 후 Supervisor는 안정적인 계획 순서에 따라 실행 웨이브를 구성한다.

1. 연속된 `parallel_safe` 작업은 하나의 동시 실행 웨이브를 이룬다.
2. 옵트인하지 않은 각 작업은 단일 작업 웨이브를 이루며 장벽 역할을 한다.
3. 로컬 세마포어는 기본적으로 활성 Specialist 네 개를 허용하고, 런타임 제한이 1~16 범위를
   벗어나면 거부한다.
4. 각 작업은 전용 결과 버퍼에 기록하며, 웨이브가 완료되면 Supervisor가 계획 순서대로 버퍼를
   병합한다.

호출 할당량의 합은 관측된 루트 잔여량 안에 유지되며 Capability 계보와 Budget Controller는
최종 디스패치 검사로 남는다. RunStore 이벤트 및 아티팩트 변경은 하나의 로컬 이벤트 루프에서
동기식으로 실행되고 await를 사용하지 않는 임계 구역이며, 증거 파일 이름은 계속 고유 요청 ID에
결속된다. Supervisor는 웨이브 구성원, 안전 계약, 동시 실행 수, 상태를 담은
`specialist.wave.started` 및 `specialist.wave.completed` 이벤트를 기록한다.

일반적인 Tool 실패는 해당 작업에 격리되며 형제 작업을 취소하지 않는다. Kill Switch 활성화,
기한 만료 또는 Rules of Engagement 중지 조건은 활성 상태인 모든 `_within_budget` 작업에서
감지되며 해당 Worker를 취소한다. 대기 중인 작업은 세마포어를 획득한 뒤 제어 상태를 다시 확인하고,
취소 후에는 디스패치하지 않는다.

고정 CTF Web 백업 GET Tool과 네트워크를 사용하지 않도록 제한된 Crypto XOR Tool은 옵트인한다.
기존 Tool은 해당 계약과 테스트가 병렬 안전성을 명시적으로 입증할 때까지 순차적으로 실행된다.

## 결과

- 독립적이며 옵트인한 Specialist는 호출, 대상, Tool 또는 위험 권한을 더 받지 않고도 실제 경과
  시간을 줄인다.
- 옵트인하지 않은 Tool과 상태를 변경하는 Tool은 보수적인 계획 순서 실행을 유지한다.
- Worker가 순서와 다르게 완료되어도 Validator와 Reporter는 계획 순서대로 정리된 결과를 받는다.
- 중지 신호 하나로 여러 활성 로컬 Worker를 취소할 수 있지만, 이미 디스패치된 안전 작업은 신호가
  관측되기 전에 시작되었을 수 있다.
- 스케줄러는 협력적이며 프로세스 로컬이다. 분산 Worker, 충돌 복구, 여러 Supervisor에는 여전히
  내구성 있는 원자적 예약과 취소 전달이 필요하다.
