# ADR 0024: 협력적 실행 취소와 로컬 정리 영수증

- 상태: Accepted
- 날짜: 2026-07-14

## 맥락

ADR 0023은 운영자 취소를 내구성 있게 만들고 취소된 Job을 디스패치하거나 커밋할 수 있는 모든
지원 Control Plane 경로를 펜싱했다. 리스된 Worker는 거부된 하트비트 또는 마무리 요청을 통해
이 펜스를 알게 된다. 이전에는 데몬이 비동기 실행 작업을 즉시 취소하는 방식으로 대응했다. 이는
Control Plane 결과 경계를 보호했지만 엔진에는 형식이 지정된 사유나 부분 증거를 봉인하고 등록된
정리를 마칠 제한된 기회를 제공하지 않았다.

하트비트를 사용할 수 없게 되거나 데몬이 종료 신호를 받았을 때도 같은 모호함이 있었다. 실행기는
형식이 지정되지 않은 `asyncio.CancelledError`만 관측할 수 있었고, 무기한 정리 중인 실행기가
종료를 지연시킬 수 있었다. Docker 정리는 예상된 취소 및 시간 초과 경로를 다뤘지만 예기치 않은
`BaseException`으로 실행 컨테이너나 해당 송신 리소스가 남을 수도 있었다.

취소에는 서로 다른 두 권한 주체가 있다. Control Plane은 내구성 있는 Run 및 Job 펜스를
소유한다. 실행기를 구동하는 프로세스는 로컬에서 관측하고 정리한 내용만 보고할 수 있다. 로컬
영수증을 외부 대상이 효과를 롤백했다거나 모든 분산 프로세스가 물리적으로 정지 상태라는 증거로
제시해서는 안 된다.

## 결정

클레임된 모든 실행은 형식이 지정된 `ExecutionCancellationContext` 하나를 받는다. 이 컨텍스트는
단방향이며 최초 기록이 우선하는 신호다. 정규화된 출처, 길이가 제한된 세부 정보, Worker가 신호를
관측한 시각을 보존한다. 이후의 실패나 종료가 취소를 처음 시작한 원인을 대체할 수 없다.
지원하는 출처는 다음과 같다.

| 출처 | Worker 경계에서의 의미 |
| --- | --- |
| `run-cancelled` | Control Plane이 Run을 취소 상태로 펜싱함 |
| `lease-lost` | Worker가 더 이상 Job 리스를 소유하지 않음 |
| `heartbeat-unavailable` | 데몬이 하트비트 채널을 통해 리스를 유지할 수 없음 |
| `daemon-shutdown` | 실행이 활성 상태일 때 데몬 중지 신호가 도착함 |
| `caller-cancelled` | 데몬 외부에서 호출된 러너를 소유한 비동기 작업이 취소됨 |

상태를 변경하는 모든 Worker 엔드포인트는 Run 펜스가 하트비트, 완료, 실패 또는 체크포인트 생성을
거부할 때 기계 판독 가능한 충돌 코드 `run_cancelled`를 사용한다. 하트비트가 일반적인 실행 중
전달 경로다. 그 밖의 리스 거부에는 `lease_lost`를 사용한다. Worker는 이 코드를 위의 컨텍스트
출처에 매핑한다. 응답 세부 정보는 일반적인 내용으로 유지한다. Operator의 취소 사유는 감사
데이터이며 Worker 자격 증명에 공개하지 않는다. 코드를 생략하는 이전 서버와도 호환되며 이 경우
`lease-lost`에 매핑한다.

데몬은 같은 컨텍스트를 `ExecutorRegistry`를 통해 신뢰할 수 있는 내장 실행기에 전달한다. Job
입력에서 실행 파일, 콜백 또는 정리 명령을 도출하지 않는다.
등록된 Job 어댑터는 키워드 전용 취소 컨텍스트를 받아야 한다. 레거시 `execute(job)` 어댑터는
Job을 클레임한 뒤 실패하게 두는 대신 Worker 시작 시점에 거부한다.

종결 하트비트 조건 또는 데몬 종료가 실행 경합에서 우선하면 Worker는 먼저 컨텍스트에 신호를
보내고 설정된 제한적 협력 유예 기간을 실행기에 제공한다. 신호를 관측한 실행기는 디스패치를
중지하고 Tool Gateway 및 Worker 리소스를 해제하며 로컬 증거를 마무리할 수 있다. 유예 기간이
만료되기 전에 반환하지 않으면 데몬은 비동기 작업 강제 취소로 폴백하고 제한된 강제 정리 시간
동안만 기다린다. 최초 원인이 두 단계 모두에서 권위를 유지한다. 리스 소유권을 잃은 후에는 해당
실행의 완료, 실패 또는 체크포인트 결과를 제출하지 않는다.

실행기가 이미 반환했다면 하트비트 또는 마무리 충돌은 새로운 협력적 정리 단계가 아니라 즉각적인
결과 펜스다. 데몬은 `executor-drained` 상태와 함께 형식이 지정된 취소 또는 리스 원인을 보존할
수 있지만, 완료된 러너에 신호를 보내거나 마무리 전용 충돌을 위해 `cancellation.json` 또는
`quiescence.json`을 합성하지 않는다.

신뢰할 수 있는 `LocalCampaignRunner`와 `PolicyToolLoopRunner`의 취소 경로는 자신이 소유한
정리가 완료된 뒤 `cancellation.json`을 쓰고 무결성 봉인을 추가한다. 이를 감싸는 신뢰할 수 있는
Job 실행기는 엔진 스택이 해제된 뒤 `quiescence.json`을 쓰고 두 번째 봉인을 추가한다. 두 영수증은
다음을 구분한다.

- 취소 출처, 길이가 제한된 사유, 관측 시각
- 강제 폴백이 필요했는지 여부와 시작 시각
- 해당 로컬 러너가 소유한 정리의 완료
- 로컬 엔진 정리와 실행기 스택의 정지 상태

Run 저장소가 생기기 전에 취소가 발생하거나 강제 폴백이 러너를 중단하면 영수증은 가능한 범위에서
최선을 다해 생성한다. 따라서 영수증 누락은 로컬 정리가 증명되지 않았음을 뜻하며, 정리에 성공한
것으로 해석하지 않는다. 영수증과 해당 봉인은 Control Plane 상태 전이가 아니라 증거 아티팩트다.

Docker 실행 정리 시도를 예기치 않은 `BaseException` 전파를 포함한 모든 종료 경로로 확대한다.
실행을 시도한 뒤 백엔드는 알고 있는 컨테이너 이름을 사용하여 제한된 프로세스 종료, 강제 컨테이너
제거, 스트림 작업 정리, 실행별 송신 해제를 시도한 다음 원래 예외를 보존한다. 취소 및 시간 초과
경로가 경합할 수 있으므로 정리는 계속 멱등적이다. CLI 시도가 실패했다는 사실은 물리적 정리 증명이
아니다.

## 신뢰 및 상태 경계

내구성 있는 Control Plane Run은 계속 `cancelled`로 바로 전이하며, 이 ADR은 `cancelling`
상태를 추가하지 않는다. 현재 API는 러너 영수증을 접수하거나 검증하거나 확인 응답하지도 않는다. 따라서
봉인된 영수증은 프로세스 로컬 진술만 뒷받침한다. 즉, 내장 러너가 형식이 지정된 신호를 관측했고
반환 전에 자신이 소유한 정리 단계를 완료했다는 진술이다.

이는 다음 항목을 입증하지 않는다.

- Tool 호출 또는 외부 시스템이 이미 커밋한 효과의 롤백
- 협력적 취소와 강제 취소를 모두 억제하는 실행기의 종료
- 원격 Worker, 자식 프로세스 또는 분산 Agent 플릿의 물리적 정지 상태
- 갑작스러운 프로세스 종료, 호스트 손실 또는 정전 후의 정리
- 대상 수준의 정확히 한 번 전달

유예 및 강제 기한은 이벤트 루프 기한이지 선점형 실제 경과 시간 보장이 아니다. 신뢰할 수 있는
실행기는 취소 핸들러가 블로킹되지 않도록 해야 한다. Python 이벤트 루프를 독점하는 동기식 정리나
무결성 해싱은 다른 asyncio 시간 초과로 중단할 수 없다. 엄격한 실제 경과 시간 내 종료에는 별도로
감독되며 종료 가능한 실행기 프로세스가 필요하고, 이는 향후 격리 경계다.

향후 프로토콜에는 `cancelling`, Worker 정리 확인 응답, 서명된 영수증 업로드, 시간 초과, Control
Plane이 권위를 갖는 물리적 정지 상태를 추가할 수 있다. 그러한 프로토콜은 기존의 즉각적인
디스패치/결과 펜스를 약화하지 않으면서 늦거나 누락된 확인 응답을 정의해야 한다. 외부 부작용 보상은
일반적인 취소 보장이 아니라 Tool 및 대상별 워크플로로 유지한다.

## 결과

- 정책 및 감사 코드는 예외 텍스트에서 원인을 추론하는 대신 안정적인 취소 원인을 받는다.
- 협력적 러너는 응답하지 않는 실행기가 데몬을 무기한 지연하도록 허용하지 않으면서 부분 증거를
  보존할 제한된 기회를 얻는다.
- 최초 기록 우선 의미론은 운영자 취소가 종료나 이후의 하트비트 실패로 다시 분류되는 것을 막는다.
- 로컬 정리 영수증은 포렌식 신뢰도를 높이지만 의도적으로 Control Plane 권한 부여, Run 상태,
  전달 의미론을 변경하지 않는다.
- 유예 및 강제 정리 한도는 운영 매개변수가 된다. Supervisor 윈도는 유예 한 번과 강제 정리 대기 윈도
  두 번 및 스케줄링 여유의 합보다 길어야 하며, 이벤트 루프가 살아 있는 동안 임베디드 백엔드 자체의
  정리 상한이 이 경계 안에 들어와야 한다.

## 검증

자동화된 테스트는 최초 기록 우선 출처 보존, 신뢰할 수 있는 실행기 레지스트리를 통한 컨텍스트 전파,
유예 기한 전 협력적 완료, 해당 기한 후 강제 작업 취소, 하트비트 및 데몬 종료 출처 매핑, 오래된
마무리 요청의 부재를 다룬다. 러너 테스트는 봉인된 Local Campaign, Tool Loop, Multi-Agent
취소 증거를 검증한다. Control Plane Campaign 실행기 테스트는 두 번의 봉인으로 이루어진 정리 및
정지 상태 시퀀스를 검증한다. Docker 백엔드 테스트는 취소, 반복 취소, 시간 초과, 성공적인 완료에
대한 컨테이너 및 송신 정리를 실행한다. 실제 Control Plane 및 Docker 테스트는 계속 환경에 따라
실행을 제한한다.
