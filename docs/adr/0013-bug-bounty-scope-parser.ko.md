# ADR 0013: 다이제스트 승인을 거치는 Bug Bounty 범위 파서

- 상태: 승인됨
- 날짜: 2026-07-13

## 배경

PAJIN의 일반 Campaign 스키마는 URL 범위, 메서드, 위험 및 capability 부여를 강제할 수 있지만,
Bug Bounty 프로그램은 사람이 작성하고 계속 변경하는 정책에서 시작한다. LLM이 이 정책을 실행
가능한 범위로 직접 변환하게 하면 모호하거나 오래된 해석이 권한 부여의 근거가 된다. 검토
문서에 속도 제한과 테스트 시간을 기록하면서 런타임이 이를 무시하는 것도 안전하지 않다.

따라서 첫 번째 Bug Bounty 수직 단면에는 권위 있는 정책 스냅샷에서 실행 가능한 Campaign으로
이어지는 결정론적 신뢰 전환이 필요하다. 자동화된 통제인 것처럼 제시하는 대신, 운영자가
수동으로 수행해야 하는 의무를 그대로 드러내야 한다.

## 결정

PAJIN에 엄격한 `BugBountyProgram` 매니페스트를 도입한다. 여기에는 원본 URI, 조회 시각, 원시
정책 텍스트, 타입이 지정된 범위 내·외 자산, 구체적인 진입점, 메서드, Tool 범주, 금지 사항,
테스트 시간대, 요청 속도, 데이터 처리 요구 사항, 보고 요구 사항 및 예산이 포함된다.

워크플로에는 별도의 두 명령이 있다.

1. `bug-bounty-review`는 정책을 검증하고 정규화하며 JSON 및 Markdown 검토 아티팩트를 작성한
   다음 정규 JSON에 대한 SHA-256 다이제스트를 계산한다. 정규화 과정에서 집합과 유사한 스칼라
   컬렉션을 정렬하므로 Python 프로세스가 달라져도 다이제스트가 안정적으로 유지된다.
2. `bug-bounty-compile`은 정확한 다이제스트와 함께 식별된 승인자, 오프셋을 포함한 승인 및 만료
   타임스탬프, 권한 부여 증거를 요구한다. 정책 스냅샷이 변경되었거나 더 오래된 것이면 승인이
   무효가 된다.

컴파일된 Campaign에는 자체 허용 규칙과 일치하고 어떤 거부 규칙과도 일치하지 않는 구체적인
진입점만 포함한다. 명시적 거부가 항상 우선한다. MVP는 T3/T4 위험과 안전하지 않은 데이터 처리
설정을 거부한다. 원본에서 누락한 경우에도 필수 금지 사항을 추가한다.

`RulesOfEngagement`에 재사용할 수 있는 두 가지 통제를 추가한다.

- `allowedToolCategories`는 명시적 허용 목록이다. 목록이 존재하면 Tool이 선언한 모든 범주가
  목록에 포함되어야 한다.
- `testingWindows`는 야간에 걸친 시간대를 포함하여 IANA 시간대 기준으로 평가한다.
  `00:00-00:00` 시간 구간은 선택한 현지 날짜 전체를 의미한다.

`maxRequestsPerMinute`는 Tool Gateway의 슬라이딩 윈도우로 강제한다. 모든 정적 정책 검사가
끝난 뒤, 어댑터 준비 또는 Worker 디스패치 전에 요청 단위를 예약하므로 실행 시도가 실패해도
프로그램 트래픽 허용량을 소비한다. Tool은 제한된 요청 비용을 선언한다. 고정 Boolean SQLi
비교는 세 번의 HTTP 요청에 대해 3단위를 예약한다. 이 한도는 하나의 Campaign 러너/Gateway
인스턴스에 귀속된다. 현재 Control Plane Job은 하나의 러너에서 전체 캠페인을 실행하여 이
경계를 유지한다.

## 안전 불변 조건

- 자유 형식 정책 텍스트는 증거로서 다이제스트에 결합되지만 실행 권한으로 해석하지 않는다.
- 보수적인 범위 매처가 지원하는 HTTP(S) URL 패턴만 컴파일한다.
- 와일드카드가 아닌 구체적인 진입점이 하나 이상 필요하다.
- 명시적 거부 규칙에 포함된 진입점은 검증에 실패한다.
- 프로그램 정책 원본에는 HTTPS가 필요하고, 승인에는 시간대 정보가 있는 타임스탬프가 필요하다.
- 기본 금지 사항에는 서비스 거부, 사회 공학, 지속성 확보, 크리덴셜 스터핑, 실제 사용자 데이터
  접근 및 데이터 유출이 포함된다.
- 이 MVP에서는 테스트 계정과 비밀 정보 마스킹이 필수다.
- 실행 가능한 자산이 고정 `boolean-sqli-lab` 프로필과 `host.docker.internal` 진입점을 사용하는
  `local-lab` 프로그램을 제외하고 사설 네트워크 실행을 거부한다.

## 결과

운영자는 정확히 어떤 정책이 실행될지 검사할 수 있으며, 정책이 변경된 뒤에도 승인이 조용히
유지될 수 없다. 새 범주, 속도 및 시간대 필드는 선택 사항이므로 기존 AI Red Team 캠페인과의
호환성은 유지된다.

이 단면은 임의의 공급자 HTML을 파싱하거나, LLM으로 범위를 추론하거나, 증거 삭제를 강제하거나,
중복 보고 시스템을 조회하거나, 최종 플랫폼별 제출물을 생성하지 않는다. 검토 문서에는 보존 및
중복 검사를 수동 통제로 명시한다. 향후 커넥터가 정책 문서를 수집할 수는 있지만, 그 출력도 타입이
지정된 이 검토 및 다이제스트 승인 경계를 통과해야 한다.

## 검증

테스트는 정규화, 정책 텍스트의 다이제스트 결합, 집합 순서 안정성, 승인 불일치와 만료, 허용/거부
중첩, 진입점 이탈, 필수 금지 사항 충돌, T3 거부, IANA 및 야간 시간대, Tool 범주 허용 목록,
가중 분당 요청 한도 소진, 사설 랩 제한, 아티팩트 직렬화, Campaign 로딩 및 실제 CLI
검토/컴파일/검증 왕복 과정을 다룬다.
